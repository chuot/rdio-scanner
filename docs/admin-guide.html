1 · What Rdio Scanner is, and what this guide covers

Rdio Scanner ingests the audio files a software-defined radio recorder writes, files them against the system, site, talkgroup, and unit they came from, and serves them to listeners as a scanner. This guide is about the server: the program you install, the flags and options that configure it, the administration interface you use to set it up, and the APIs it answers on.

A deployment is one program. It listens on one address, keeps one database, and offers two interfaces: the main interface that listeners open, and the administration interface at /admin/ that you configure the deployment with. Everything in this guide is about the server and the administration interface.

What this guide does not cover

The listener web app — the page a listener opens on the main address, with its talkgroup list, its call history, and its player — is documented in the web app guide. The native mobile applications are Saubeo Solutions' own clients. Neither is covered here, and no screenshot in this guide shows a listener screen. Where a chapter needs to say something about what a listener sees, it says it from the server's side: the option that changes it, the credential that unlocks it, the endpoint that serves it.

This guide is the path from nothing to a working deployment, and it is written to be read in order once and consulted afterwards. The other documents in the repository stay the authorities for their own subjects, and this guide links to them instead of duplicating them:

2 · How audio flows through the server

Audio arrives in one of two ways, is filed against the configuration, and leaves toward listeners. Understanding the path explains most of what you will configure, and most of what can go wrong.

In

A recorder's output reaches the server by one of these paths:

  • Dirwatch — the server watches a directory the recorder writes into, reads each new audio file, and takes the call's identity from the file's name, its MP3 tags, or its sidecar JSON, depending on the recorder type you chose for that watch. See Getting audio in.
  • The upload endpoints — a recorder posts the audio and its metadata to POST /api/call-upload, or posts trunk-recorder's JSON sidecar to POST /api/trunk-recorder-call-upload, presenting an API key. See The HTTP REST API.

Both paths end at the same ingest. The ingest resolves the system, site, talkgroup, and unit the metadata names against your configuration. When Auto populate is on, an identity the configuration does not know is created on the spot; when it is off, the call is refused and the log says why. The ingest then converts the audio to H.264 m4a when the Audio conversion option asks for it, which is what makes recordings small and playable in a browser, and files the call in the database with its audio.

Audio lives in the database

The server stores the recordings inside the database, not as files beside it. The directory the server serves holds the database, the configuration file, and the server's own state — the recordings are rows. That is what makes a single file the whole archive of a deployment, and it is what you back up.

Out

  • Listeners read the call history and the recordings over the HTTP REST API, and follow live calls over the server's real-time channel. The REST API is free to use for any purpose; the real-time channel is proprietary, as the access policy states.
  • Downstreams forward calls to another Rdio Scanner deployment, presenting an API key there, scoped to the systems and talkgroups you choose.

What the server keeps

What the server holds, and where
ThingWhere it livesChanged by
Systems, sites, talkgroups, units, groups, tags, access codes, API keys, dirwatches, downstreams, optionsThe database, edited as sections in the administration interfaceYou, in a section, saved with that section's save bar

Worked recorder configurations are in docs/examples/trunk-recorder and docs/examples/rtlsdr-airband.

Machines

The server is a single Go binary and does not need much: a 1 GHz-class machine runs a small deployment comfortably, and a Raspberry Pi 3 or newer runs a typical one. Plan for disk, not for CPU: recordings accumulate, and the size of your database is the size of your retention. A deployment that keeps seven days of a busy system is measured in gigabytes, and the Prune days option is what bounds it.

The database is a requirement in its own right. SQLite needs nothing — the server writes one file in its data directory, which is the right choice for a single-instance deployment. MariaDB, MySQL, and PostgreSQL need a server you run and the connection flags that name it. See The database.

If you are building from source

  • Go 1.26 or newer.
  • Node.js 20 or newer, for the web applications the server carries inside it.
  • podman, for building the container image.
  • A C toolchain, only if you build the bundled ffmpeg yourself.

The whole procedure is in Compiling.

4 · Installation

Three ways to install: the precompiled archive for your platform, the container image, or the source. All three produce the same server; they differ in how you upgrade it and where its data lives.

From the precompiled archive

Download the archive for your platform and architecture from the releases page, and extract it where the server will live. An archive carries the binary and the documentation that goes with it:

  • the rdio-scanner executable for your platform;
  • CHANGELOG.md;
  • the platform page for the archive's own system, under docs/platforms/;
  • this guide, at docs/admin-guide.html;
  • the web app guide and the FAQ, under docs/;
  • the pictures those documents point at, under docs/images/;
  • FFMPEG.md, on the platforms that carry their own ffmpeg.

The archive's layout is the repository's, so the relative links between those documents resolve inside the extracted folder. Put the folder somewhere the server can write: the server writes its database, its configuration file, and its state into the folder it was started from. 

cd /opt
unzip ~/Downloads/rdio-scanner-linux-amd64-v8.0.0.zip
cd rdio-scanner-linux-amd64-v8.0.0
./rdio-scanner

The per-system details — paths, the service mode, the firewall — are on the platform page for the system you installed on: Linux, Windows, macOS, FreeBSD.

From the container image

A container image is published for each release. The container serves from /app/data, so the data you must keep is whatever you mount there, and the mount must be writable by the user the container runs as: 

mkdir -p ~/.rdio-scanner

docker run --detach --name rdio-scanner \
    --env TZ=America/Toronto \
    --publish 3000:3000 \
    --restart always \
    --user $(id -u):$(id -g) \
    --volume ~/.rdio-scanner:/app/data \
    chuot/rdio-scanner:latest

Create the data folder before the first run. A folder the container daemon creates on your behalf is owned by the wrong user, and the server refuses a directory it cannot write — the same rule the server applies on a plain installation.

The documented compose file, the volume layout, the user, and the port mapping are in the container guide. Two things an administrator running the container should know: the directory-watcher section is removed from the administration navigation when the server's environment names the container, because a watched directory inside a container is a container path and not yours; and the container's data directory is /app/data, so the database file you back up is the one inside the mount.

From source

With Go 1.26 and Node 20 installed, the build tool does the work: 

go run ./cmd/build client     # the web applications the server carries
go run ./cmd/build server     # one binary, into dist/<target>/
go run ./cmd/build dist       # every release archive, into dist/
go run ./cmd/build container  # the container image, locally

server builds the web applications first, so the binary carries them and serves them with no separate web server. dist writes the archives for every platform in the release matrix. The details, including the ffmpeg bundle, are in Compiling.

5 · First run

A fresh server needs one flag to run: it serves, creates its own database, and tells you in its console where it answers. The three things to do next are all in the administration interface, and the interface tells you what they are.

Starting it

./rdio-scanner

The server writes everything into its base directory: the executable's own folder, and when that folder is not writable, a folder named Rdio Scanner inside your home directory. -base_dir names a folder of your choosing instead, and that is the flag to set on a deployment you intend to keep. The server refuses to start when the base directory is not writable, and says so on the console.

On a first run the console says:

The two addresses are the same port by default: the listener interface at / and the administration interface at /admin/. The signing secret is how the server signs the sessions you open; it is generated once, stored in the database, and changing it ends every session that was open.

Logging in

Open http://localhost:3000/admin/ in a browser. The server ships with one administrator and the password rdio-scanner. Log in with it, and change it immediately — the interface tells you to, in the banner it shows you.

The login endpoint answers a token, and the browser keeps it for the session. The server signs tokens with its secret and keeps the last five it issued, so signing in ends the sessions older than that. Three failed logins from one address lock that address out for ten minutes; the server logs the attempts under the login subsystem.

The banner that lists what is missing

The first page after login is a card that lists what a deployment still needs. It is computed from your configuration, so it clears itself as you work, and it names the control that clears each item:

The items the banner lists on a fresh deployment
LevelItemCleared by
WarningYou are using the default admin password, please change it from the tools / admin password menu.Tools ▸ Change password
InfoNo systems defined. Define one from the Systems menu, or turn on Options ▸ Auto Populate to have them created for you.The Systems section, or the Auto populate option
InfoNo apikeys or dirwatch defined. Set at least one to allow ingesting audio files.The API Keys section or the Dirwatch section

A first configuration, in order

  1. Change the administration password in Tools.
  2. Add a system in Systems — a system is the top of the hierarchy the listener browses.
  3. Give the recorder a way in: an API key for a recorder that posts calls, or a dirwatch for a recorder that writes files. See Getting audio in.
  4. Watch the Logs section while the first calls arrive. The ingest names the system and talkgroup it resolved, and says when it refused a call and why.

Each section saves with its own save bar, and the save is a write to the running server: the change is announced to every other open administration session, and the server files a the configuration changed entry in the log. Nothing needs a restart, except the flags.

Writing the flags to a file

Flags are read at start-up. Once you have the flags you want, -config_save writes them to rdio-scanner.ini in the base directory, and the server reads that file on every later start, so the flags no longer have to be repeated on the command line: 

./rdio-scanner -listen ":3000" -base_dir /opt/rdio-scanner -config_save
./rdio-scanner          # reads /opt/rdio-scanner/rdio-scanner.ini

Command line flags win over the file. The file is plain INI, one flag per line, and it is the file to keep with your backup — it is the deployment's own shape, in text.

1 · What Rdio Scanner is, and what this guide covers

Rdio Scanner ingests the audio files a software-defined radio recorder writes, files them against the system, site, talkgroup, and unit they came from, and serves them to listeners as a scanner. This guide is about the server: the program you install, the flags and options that configure it, the administration interface you use to set it up, and the APIs it answers on.

A deployment is one program. It listens on one address, keeps one database, and offers two interfaces: the main interface that listeners open, and the administration interface at /admin/ that you configure the deployment with. Everything in this guide is about the server and the administration interface.

How the name is said

Rdio is Radio spelled the way the project spells it: the name is pronounced Radio Scanner and written Rdio Scanner.

2 · How audio flows through the server

Audio arrives in one of two ways, is filed against the configuration, and leaves toward listeners. Understanding the path explains most of what you will configure, and most of what can go wrong.

In

A recorder's output reaches the server by one of these paths:

  • Dirwatch — the server watches a directory the recorder writes into, reads each new audio file, and takes the call's identity from the file's name, its MP3 tags, or its sidecar JSON, depending on the recorder type you chose for that watch. See Getting audio in.
  • The upload endpoints — a recorder posts the audio and its metadata to POST /api/call-upload, or posts trunk-recorder's JSON sidecar to POST /api/trunk-recorder-call-upload, presenting an API key. See The HTTP REST API.

Both paths end at the same ingest. The ingest resolves the system, site, talkgroup, and unit the metadata names against your configuration. When Auto populate is on, an identity the configuration does not know is created on the spot; when it is off, the call is refused and the log says why. The ingest then converts the audio to H.264 m4a when the Audio conversion option asks for it, which is what makes recordings small and playable in a browser, and files the call in the database with its audio.

Audio lives in the database

The server stores the recordings inside the database, not as files beside it. The directory the server serves holds the database, the configuration file, and the server's own state — the recordings are rows. That is what makes a single file the whole archive of a deployment, and it is what you back up.

Out

  • Listeners read the call history and the recordings over the HTTP REST API, and follow live calls over the server's real-time channel. The REST API is free to use for any purpose; the real-time channel is proprietary, reserved for Saubeo Solutions and its native applications, as chapter 27 states.
  • Downstreams forward calls to another Rdio Scanner deployment, presenting an API key there, scoped to the systems and talkgroups you choose.

Machines

The server is a single Go binary and does not need much: a 1 GHz-class machine runs a small deployment comfortably, and a Raspberry Pi 3 or newer runs a typical one. Plan for disk, not for CPU: recordings accumulate, and the size of your database is the size of your retention. A deployment that keeps seven days of a busy system is measured in gigabytes, and the Prune days option is what bounds it.

The database is a requirement in its own right. SQLite needs nothing — the server writes one file in its data directory, which is the right choice for a single-instance deployment. MariaDB, MySQL, and PostgreSQL need a server you run and the connection flags that name it. See The database.

4 · Installation

Three ways to install: the precompiled archive for your platform, the container image, or the source. All three produce the same server; they differ in how you upgrade it and where its data lives.

From the precompiled archive

Download the archive for your platform and architecture from the releases page, and extract it where the server will live. An archive carries the program and the one document that operates it:

  • the rdio-scanner executable for your platform;
  • this guide, at docs/admin-guide.html;
  • FFMPEG.txt, the licence of the bundled ffmpeg, on the platforms that carry their own ffmpeg.

The guide carries its own stylesheet and its own pictures, so an extracted archive needs nothing from the network and nothing from the repository. Put the folder somewhere the server can write: the server writes its database, its configuration file, and its state into the folder it was started from. 

cd /opt
unzip ~/Downloads/rdio-scanner-linux-amd64-v8.0.0.zip
cd rdio-scanner-linux-amd64-v8.0.0
./rdio-scanner

The per-system detail — where the server lives on that system, its service commands, its firewall, and what its archive contains — is in chapter 21, one sub-section for each of Linux, Windows, macOS, and FreeBSD.

From the container image

A container image is published for each release. The container serves from /app/data, so the data you must keep is whatever you mount there, and the mount must be writable by the user the container runs as: 

mkdir -p ~/.rdio-scanner

docker run --detach --name rdio-scanner \
    --env TZ=America/Toronto \
    --publish 3000:3000 \
    --restart always \
    --user $(id -u):$(id -g) \
    --volume ~/.rdio-scanner:/app/data \
    chuot/rdio-scanner:latest

Create the data folder before the first run. A folder the container daemon creates on your behalf is owned by the wrong user, and the server refuses a directory it cannot write — the same rule the server applies on a plain installation.

The compose file the project documents is the same run command written as a service: 

services:
  rdio-scanner:
    image: chuot/rdio-scanner:latest
    container_name: rdio-scanner
    environment:
      - TZ=America/Toronto
    ports:
      - "3000:3000"
    restart: always
    user: "1000:1000"
    volumes:
      - ./data:/app/data

Two things an administrator running the container should know. The directory-watcher section is removed from the administration navigation when the server's environment names the container, because a watched directory inside a container is a container path and not yours — mount the recorder's folder into the container and watch the mount. And the container's data directory is /app/data, so the database file you back up is the one inside the mount: Backup and restore.

From source

With Go 1.26 and Node 20 installed, the build tool does the work: 

go run ./cmd/build client     # the web applications the server carries
go run ./cmd/build server     # one binary, into dist/<target>/
go run ./cmd/build dist       # every release archive, into dist/
go run ./cmd/build container  # the container image, locally

server builds the web applications first, so the binary carries them and serves them with no separate web server. dist writes the archives for every platform in the release matrix: FreeBSD on amd64, Linux on 386, amd64, arm, and arm64, macOS on amd64 and arm64, and Windows on amd64. container builds the container image on the machine you run it on, for the architecture of that machine.

Five of the eight builds carry their own ffmpeg: the four Linux builds and the Windows build. The macOS and FreeBSD builds do not — they use the ffmpeg their host installs, so a deployment on those platforms installs ffmpeg itself. The build compiles a target's ffmpeg from the project's own recipe before it compiles the server that embeds it, so a server built before its ffmpeg exists is not a server that ships without one. The licence of the ffmpeg a release carries travels in that release, beside this guide.

The build tool takes the release name and an output path: --pre names a pre-release suffix carried in the version line the server reports, and -o sends the output somewhere other than dist/. go run ./cmd/build version prints the version the server will report, and clean takes the build's output away.

5 · First run

A fresh server needs one flag to run: it serves, creates its own database, and tells you in its console where it answers. The three things to do next are all in the administration interface, and the interface tells you what they are.

Starting it

./rdio-scanner

The server writes everything into its base directory: the executable's own folder, and when that folder is not writable, a folder named Rdio Scanner inside your home directory. -base_dir names a folder of your choosing instead, and that is the flag to set on a deployment you intend to keep. The server refuses to start when the base directory is not writable, and says so on the console.

On a first run the console says:

The two addresses are the same port by default: the listener interface at / and the administration interface at /admin/. The signing secret is how the server signs the sessions you open; it is generated once, stored in the database, and changing it ends every session that was open.

Logging in

Open http://localhost:3000/admin/ in a browser. The server ships with one administrator and the password rdio-scanner. Log in with it, and change it immediately — the interface tells you to, in the banner it shows you.

The login endpoint answers a token, and the browser keeps it for the session. The server signs tokens with its secret and keeps the last five it issued, so signing in ends the sessions older than that. Three failed logins from one address lock that address out for ten minutes; the server logs the attempts under the login subsystem.

A first configuration, in order

  1. Change the administration password in Tools.
  2. Add a system in Systems — a system is the top of the hierarchy the listener browses.
  3. Give the recorder a way in: an API key for a recorder that posts calls, or a dirwatch for a recorder that writes files. See Getting audio in.
  4. Watch the Logs section while the first calls arrive. The ingest names the system and talkgroup it resolved, and says when it refused a call and why.

Each section saves with its own save bar, and the save is a write to the running server: the change is announced to every other open administration session, and the server files a the configuration changed entry in the log. Nothing needs a restart, except the flags.

Writing the flags to a file

Flags are read at start-up. Once you have the flags you want, -config_save writes them to rdio-scanner.ini in the base directory, and the server reads that file on every later start, so the flags no longer have to be repeated on the command line: 

./rdio-scanner -listen ":3000" -base_dir /opt/rdio-scanner -config_save
./rdio-scanner          # reads /opt/rdio-scanner/rdio-scanner.ini

The file is plain INI, one key = value per line, and it is the file to keep with your backup — it is the deployment's own shape, in text. Read the next chapter for which keys the file carries, and for the precedence the server applies between the file and the command line.

The ini file, and which value wins

The server parses the command line, then reads rdio-scanner.ini from the base directory and overlays it. The file is plain INI, no section header, one key per line: 

db_type = postgresql
db_host = db.internal
db_name = rdioscanner
db_user = rdio
db_pass = <the password>
db_sslmode = require
listen = :3000
ssl_auto_cert = scanner.example.org
trusted_proxies = 127.0.0.1, 10.0.0.0/8
mcp_server = true
bcrypt_cost = 12

The keys the file can carry are:

bcrypt_cost, db_connect_timeout, db_file, db_host, db_name, db_pass, db_port, db_sslmode, db_tls, db_type, db_user, listen, mcp_server, ssl_auto_cert, ssl_cert_file, ssl_key_file, ssl_listen, trusted_proxies

The precedence is the detail that surprises people, so it is stated plainly: for a key the file names, the file wins; a key the file does not name leaves the command line's value alone. A missing or unreadable file leaves every flag as you typed it. -base_dir, -config, -admin_password, -cmd, -service, and -version are never read from the file: the base directory and the file name are how the server finds the file at all, and the rest are ways of running the program, not settings it runs with.

-config_save writes the file from the flags as parsed on that command line, prints rdio-scanner.ini file created, and stops. It writes the database keys for the backend you chose: a SQLite deployment writes db_file and db_type; a server-side backend writes host, name, user, password, TLS, SSL mode, connect timeout, port, and type. Because the file then outranks the command line, the usual path is: start once with the flags you want, add -config_save, and start the server with no flags at all.

The file holds secrets

The database password is in that file, in plain text. Restrict it — chmod 600 rdio-scanner.ini — and give the base directory to the user the server runs as and to nobody else. The administration password is not in the file: it is hashed in the database.

What the server refuses at start-up

Each of these stops the start, with the reason on the console, before a port is opened:

  • a base directory the server cannot write;
  • a -db_type outside the four supported backends;
  • a -bcrypt_cost outside 10 to 14 — a cost typo would hash the administrator credential at a cost you never asked for, and the credential on record is the one thing a typo must not touch;
  • a -db_connect_timeout that is not a duration.

A TLS listener that cannot start is the start-up failure that does not stop the server: the plain address keeps serving, and the log says the TLS listener failed. See TLS and HTTPS.

The recordings are rows, not files. The base directory holds the database and the configuration file; the audio is inside the database, which is why a deployment is one file to back up, and why the database grows with your retention.

Retention

The retention pass deletes the calls and the log entries older than the Prune days option, calls first and the log after, and files what it removed under the prune subsystem: retention pass removed 1 234 calls and 5 678 log entries. Setting the option to 0 disables the pass, and the deployment keeps everything it has ever ingested.

The pass runs on the server's own schedule, against the server's clock, so the timezone matters on a deployment where the day boundary is meaningful. Pruning is not a backup: it is the opposite of one. Set the retention only after you have the backup you want.

When an older database is opened

A database written by an older server is migrated on the first start of this one: the schema is brought forward, the groups and tags the legacy server kept in the options are made into their own rows, and the log table is rebuilt. The rows the migration read and could not carry into the new shape are written to the migration archive with the table and row they came from, the reason, and the moment they were archived. Nothing is silently dropped.

The pass is re-run on the next start, and rows already archived archive as nothing rather than colliding, so a migration that stopped partway continues. Chapter 24 is the path for a version 5 deployment, and what to check after a migration.

Keeping it healthy

  • Back up the database file while the server is not writing to it, or take the backup from the database server's own tools. See Backup and restore.
  • Give the server-side backends a database user with the narrowest grant that lets the server work: the database, its tables, and nothing else.
  • Watch the database subsystem in the log. Connection failures, statements that failed, and the migration's own lines are filed there.
  • Do not edit the tables by hand. The administration interface is the path the server expects, and a hand-edited row is a row the server will read as its own.

8 · The administration interface

The interface at /admin/ is where a deployment is configured. It is one page served by the server, it edits the configuration through the running server, and it shows you what the server is doing while you work.

Logging in, and what a session is

The login sends the password to the server and the server answers a session token. The browser keeps that token for the session, and every request the interface makes carries it. The token is signed with the server's signing secret and has no expiry of its own: the server keeps the last five tokens it issued, so signing in four times ends the sessions older than that, and a server that generates a new secret ends every session that was open before it.

Three failed logins from one address lock that address out for ten minutes. The server answers a refused login with the same message it answers a wrong password with — it never says how many attempts are left — and files the lockout in the log as too many login attempts from the address. Behind a reverse proxy, the address the server sees is the proxy's own unless you name the proxy as a trusted proxy: see Reverse proxies.

Rows, the save bar, and the conflict banner

Each section is a list of rows, and a row is collapsible: collapsed it shows the row's identity, expanded it shows every field it carries. Add a row with the section's add control, delete it with the row's own delete button. Nothing is written while you type.

The save bar at the bottom of a section is what writes your work. It is enabled when the section has unsaved changes and they are valid, and it says what is unsaved. Save sends the section to the running server; Discard throws the unsaved work away and reloads the section as the server has it.

Two sessions editing the same section is the case the conflict banner is for. When another session saved the section while you were editing it, the banner appears above the list with Reload from server and Discard: reload takes the server's current version and lets you re-apply your change on top of it, and discarding your work is the honest way out of a collision you did not want. Saving over another administrator's work is what the banner exists to stop.

A save is a write to the running server, and the server tells every other open administration session that the configuration changed, over the connection the interface holds open for exactly that. The server files the configuration changed in the log. No restart is involved: the sections are live. The flags are not — see the flags chapter.

  • The Logs section is the server's own account of what it did, and it is where a problem is diagnosed. It is on the log chapter.

An open server and a restricted one

The Access section decides which kind of server you are running. An empty access list is an open server: every listener is given the whole configuration and is never asked for a code. A list with one entry in it is a restricted server, and every listener must present a code before the server sends it anything.

That is the whole switch, and it is worth being deliberate about. Adding the first access code changes a server that anyone could listen to into one that answers nobody until they present a code — including the applications that were listening a minute ago.

What a listener is told

The server checks a code in a fixed order, and the order is visible to the listener, so it is worth knowing before someone phones you about it.

The listener's outcomes, in the order the server checks them

Five attempts is the limit, counted twice over: once for the session and once for the address it came from. A code that is accepted clears both counters. A code that is refused does not, whichever reason refused it, which is what makes the counter a limit on trying rather than a limit on being wrong.

A code is a credential, so the server never writes one in its log. The entry that names a refused code names the address it came from, and the entry that names an expired or locked code names the ident — never the code. A guessing tool must not be able to fill the log view, which is why the warning about an invalid code is said once per window and not once per guess.

A key you add with the section's add control starts scoped to Everything. A key whose scope is empty uploads nothing, so a key you have scoped to systems and then unticked everything under is a key that has stopped working — the upload is refused, and the log says the key is not valid.

Where the key goes depends on the ingest path. A watched directory needs no key at all — the directory is the credential, which is why watched directories are yours to protect. An upload to /api/call-upload carries the key in the key form field of the multipart request, and a trunk-recorder upload carries it in the same field. The scope dialog

Access codes, API keys, and downstreams all open the same dialog, because the server scopes all three against the same pair: a system and a talkgroup.

  • Everything is the whole deployment: every system, every talkgroup, and every one added later.
  • Groups and Tags tick a whole group or tag at once. A box in its third state means the scope covers part of that group, which is what a group you ticked and then narrowed inside the Systems list looks like.
  • Systems lists each system with its talkgroups under it. Ticking a system ticks its talkgroups; unticking one talkgroup leaves the rest.

A system in the scope with no talkgroups named under it is not in the scope at all. That is the shape of the stored scope, and it is the one thing about the dialog that bites: a system whose talkgroup list is empty grants nothing, so a listener holding that scope sees a live feed with nothing in it and an upload to that system is refused.

For a downstream, the scope is not what the downstream may see — it is the calls this server forwards to it. A downstream scoped to two systems forwards those systems' calls and nothing else, and a downstream with no scope forwards nothing.

The dialog is on the administration interface chapter, photographed with the groups and tags named.

Scoping is a grant, not a filter. A listener whose scope covers a talkgroup can hear it; a listener whose scope does not cannot, and there is no setting on the listener's side that changes that. When someone reports a talkgroup they cannot hear, the answer is in that listener's scope, and the summary line under Choose systems — all systems and talkgroups or some — is where you start.

Trunk Recorder on another host

Trunk Recorder's uploadScript property runs a script for each finished call, with the system identifier as its first argument and the recording's full path as its second. This is the script the repository carries; it posts the recording and its sidecar and then removes them. 

#!/bin/bash
#
# Use this script with Trunk Recorder's uploadScript system property in its
# config.json file:
#
#   {
#     ...
#     "uploadScript": "upload-call.sh 7537"
#     ...
#   }
#
# The first argument is the Rdio Scanner system identifier; Trunk Recorder adds
# the full path of the audio file as the second argument.

# The API key configured in your Rdio Scanner instance.
apikey=b29eb8b9-9bcd-4e6e-bb4f-d244ada12736

basename="${2%.*}"

curl -sS http://127.0.0.1:3000/api/trunk-recorder-call-upload \
     -F "key=${apikey}" \
     -F "audio=@${basename}.wav;type=audio/wav" \
     -F "meta=@${basename}.json;type=application/json" \
     -F "system=${1:-0}"

# The audio file and its JSON sidecar are then deleted.
rm -f ${basename}.*

Change the key and the address, and give Trunk Recorder your system's identifier. When the recorder and the server are on the same host, watch the capture directory instead — a dirwatch needs no key, no script, and no network.

Identifiers, and how a recording finds its talkgroup

Every one of these rows carries an identifier that belongs to your recorder, not to the database. The server keeps its own identifiers, and the row's Id is the reference the recorder and the listener applications use. When a recording arrives, the server looks for the system and the talkgroup in a fixed order:

  1. the database identifier, when the upload names one;
  2. then the recorder identifier you typed into the row;
  3. then the label, when the recording names a system or talkgroup by name.

Nothing is created by that lookup on its own — that is auto populate's job, and it is a separate decision. A recording that matches nothing is a Call ingest log entry naming the recording, which is where a capture box that stopped appearing is diagnosed.

Two rows carrying the same identifier in one system is a deployment that files calls against whichever row the lookup reaches first. The interface marks the second row Id is already defined and keeps the section's Save disabled until you fix it; the server's own endpoint does not refuse the identifier, so a configuration written through the API can carry the duplicate. When calls land on a talkgroup with a label you did not expect, the duplicate identifier is what to look for.

Alerts, colours, and which one wins

Alert tones and LED colours are set at four levels — group, tag, system, talkgroup — and the assignment order is group, then tag, then system, then talkgroup. A talkgroup in a group that carries an alert takes the group's alert, whatever its system says. The colour works the same way, and the default colour is green.

Groups and tags are the two scope shortcuts that survive a system's growth. For a deployment whose listeners follow a system as it grows, groups are the scope that keeps working.

The normalization modes need a ffmpeg built with the loudnorm filter; the server checks the program it has at startup, and a build without the filter converts in the plain mode whatever the option says. The conversion is a step after the call is filed, and a deployment with a broken ffmpeg keeps its calls.

Retention

Prune Days is the deployment's memory: the call history, the recordings, and the log entries older than that many days are removed by a pass that runs once an hour. It is the option that decides whether a deployment fills its disk, and the Retention subsystem is where you check that it is running. The detail is on the log chapter.

The administrator password and the server's signing secret live in the options table and are not controls on this section: the password is changed in the Tools section, on the tools chapter. The flags — the address the server answers on, the database it opens, TLS, the service — are not options either, and they are set at startup: the flags chapter.

Options are saved as a section, and the section is written whole. Two administrators in the Options section is the case the conflict banner is for: the banner appears when the other session saved while you were editing, and Reload from server is the answer. See the administration interface.

14 · Logs

The server writes down what it does, and every entry says which part of the server wrote it. On a deployment that is misbehaving you do not read everything the server said: you ask for what the directory watchers said, or what the last hour of logins said, and read only that.

The log is in three places, and it is the same log

  • the Logs section of the administration interface, at /admin/;
  • the server's console, which is what journalctl -u rdio-scanner shows on a service deployment;
  • the logs table of the database.

The levels are Informative, Warning, and Error. A line that only ever went to the console — the base folder the server serves, the server stopping, a new signing secret, and everything the server said about a listener connection it could not read, could not understand, or could not write to — is written to the log as well, so it is searchable instead of something you had to be watching when it happened. The three notices that name the addresses the server is listening on are console only: they say where to point a browser, not what the server did.

A stored message says what happened, in the language of the system, and where something failed the failure's own text follows it. On the console and in the service log the same entry carries its level and its subsystem in front of it, so the subsystem split reaches the deployments diagnosed from a terminal: 

warn dirwatch: the watcher for /data/rdio/watch/trunk stopped: no such file or directory

That is what you grep for: journalctl -u rdio-scanner | grep ' dirwatch: '.

15 · Tools

The Tools section is where a deployment moves in and out of files: the configuration out as one JSON file, a configuration back in, a talkgroup or unit list from another application, and the administrator password.

Export and import the configuration

Export config downloads the saved configuration as one JSON file: every section as the server has it, with the working copies of open sections left out. It is the deployment's own record — the file you keep before an upgrade, the file you copy to a second deployment, and the file you attach when you ask for help.

Import loads a configuration JSON file into the sections' working copies. It does not write anything: the caption under the picker says it plainly, because the difference matters. After an import, each section holds unsaved changes and its save bar is enabled, and the deployment changes only when you save the sections you want to apply.

An import is a whole configuration arriving in a running deployment. Save the sections you checked, and discard the ones you did not: the sections you leave alone keep their unsaved import in the working copy, and a save bar pressed later writes them. Importing a configuration from another deployment brings its access codes, its API keys, and its downstreams with it.

Import talkgroups and units from CSV

A talkgroup list from another application is imported per system. Pick the system, choose the CSV file, and the section shows you the rows it is about to write before you import them.

The CSV imports

Change the password

The password panel takes the current password, a new one, and the new one again to verify it. The new password is at least eight characters, and the server checks the current password before it writes anything: a change with the wrong current password is refused, and the log says the password was not changed and why.

A server still running the password it shipped with says so in the todos banner at the top of the administration interface, and the banner is quiet once the password is changed. Changing the password does not end the sessions that are open: the session token is signed with the server's signing secret, not with the password. See security hardening.

A password you have lost is recovered with the program itself, not with the interface: the -admin_password flag stores a new administrator password on the machine where the server runs, where the database is. The password you type is a command-line argument, so it is visible to the other processes on that machine — run it where the server runs, and not in front of a share.

Two connections, not requests

Two paths take a connection rather than a request.

  • The listener connection is taken over the address the scanner webapp is served from: the same path answers a browser and a listener, and the upgrade header decides which. The server asks a restricted server's listeners for an access code, sends the configuration their scope grants, and streams the calls. This connection is reserved for Saubeo Solutions and its native applications; the position is stated in chapter 27.
  • The administration connection at /api/admin/config is how an open administration session learns that the configuration changed: a save on the server is broadcast to every session, which is what makes the conflict banner appear on a page that is already open.

What the endpoints answer

  • Administration endpoints answer JSON, and a failure is answered with the status and an empty body.
  • The upload endpoints answer plain text, because the recorders that post to them read a line, not a JSON document: Call imported successfully. when the call was taken, Invalid API key for system <nil> talkgroup <nil>. with 401 when the credential refused it. See the upload endpoints.
  • A method an endpoint does not take is answered 405; the upload endpoints answer it with a line of text, and file it in the log, because a recorder posting with the wrong method is a standing misconfiguration.

The endpoints that write are the endpoints the interface uses, and they write to the running server: a configuration written through the API takes effect at once, is broadcast to the open administration sessions, and is filed in the log as a configuration change. The flags are not in this list — the flags chapter is where those are set.

Reading the contract

The contract the server publishes is machine-readable and is what the OpenAPI section reads. It names each path, its method, the credential it takes, and the shape of the bodies. The section is the quickest way to see what a running server answers, and it is the source the endpoint table above is checked against.

17 · The MCP server

The server can answer the Model Context Protocol: an assistant connected to your deployment can read the configuration, search the calls and the log, and — when it presents the administrator's credential — change the deployment. It is off by default, and it is mounted at /mcp.

Enabling it

The endpoint exists only when the server is started with -mcp_server, and the ini file carries the same setting as mcp_server = true. With the flag off, the path is not registered: the server answers nothing there, and the surface leaves no trace in the log.

Who reaches it, and how far

The endpoint has no credential of its own. It reads the same two credentials the rest of the server reads, and the credential decides the tier.

The two tiers, and what each one may do
Credential presentedTierWhat it opens
Authorization with an administrator session tokenAdministratorRead and write: the whole endpoint
X-Access-Code with a listener access codeRead-onlyThe call history and the configuration reads, inside the scope that code carries

Anything the server does not acceptrefusedAn empty 401, and the protocol handler is never reached

The administrator's credential is examined first, so a stale access-code header on an administrator's request cannot get the administrator refused as a listener. A refusal is filed under the Assistant surface subsystem naming the address the request came from — what the caller presented is a credential, and a credential is not written in the log.
